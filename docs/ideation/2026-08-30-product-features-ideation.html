Grounding Context

Codebase Context

Our Recipes 0.11.0 is a SvelteKit + Supabase family recipe PWA: public discover (title search, course, effort), private drafts, cooking mode, Cooked! ratings, a device-local shopping list, and MCP tools that create or edit only private recipes. The manifest line is “Save family favorites, share them with anyone, and keep cooking together.”

Recipes are single-author. Non-authors hit 404 on private rows; the only share path is a public URL or “Make my version,” which inserts a full private clone with no parent id. The shopping list lives in localStorage; cooking progress lives in sessionStorage. PWA navigations are NetworkOnly — the list survives offline, recipes do not. Allergens (EU-14) are stored and shown on cards but never used as a filter. There are no household, invite, URL-import, collection, meal-plan, print, or timer surfaces.

External 2026 signal: clip → list → plan is saturated. Remaining gaps that still fit this product are capability-based family share (not a social network), dietary remix that keeps the original, offline cook, and leftovers-without-a-calendar. Institutional learnings are thin; NEXT-STEPS.md still lists views and cooking mode as future work though both already ship.

Idea 1

1. Guest cook ticket

A signed-in author mints a time-bounded capability for one private recipe: open it, run cooking mode, add scaled ingredients to a list — without listing it on home and without handing over edit rights. When the ticket expires, the guest is back to 404. The author’s row stays the only copy.

This is the missing third verb between “publish to strangers” and “fork into my book.” The hero already promises share-with-anyone; the server only offers is_public or nothing.

Description
Capability link or code scoped to one recipe and a cook window. Guest can read, cook, and shop from it. No home listing, no edit, no permanent household membership.
Axis
Household sharing and sync
Basis
direct: private recipes 404 unless author_id matches the viewer; ShareButton only emits the public URL; duplicateRecipe is the only non-public path and creates a new author-owned clone.
Rationale
Families text a recipe for tonight. Forcing publish trains people to put grandma’s stew on the public grid, or to fork until nobody knows which copy is real.
Downsides
Token/ACL work; abuse if tickets are too durable; does not sync two phones’ checklists by itself (pair later with a cook event if needed).
Confidence 85% Complexity Medium
Idea 2

2. Overlay remix with lineage

Stop treating “Make my version” as a severed full copy. Keep the original as the type specimen and store a named overlay — dairy-free, half-batch, extra thyme — with a parent recipe id. Cooking mode and the shopping list apply the delta. The heirloom row does not fork.

Description
Add parent lineage (and optional transform note) on remix. Prefer a thin overlay over copying every field. Browse can later walk “from this recipe” without inventing author profile pages.
Axis
Recipe capture and remix
Basis
direct: duplicateRecipe copies ingredients, steps, body, servings, allergens, course, and effort into a private row titled with a copy suffix, and records no source id. external: 2026 keepers still struggle at dietary remix that preserves the original.
Rationale
A family book’s value is lineage. Full-copy remix is how “this is still grandma’s stew, Tuesday’s version” disappears.
Downsides
Overlay merge rules get hard (conflicting ingredient edits); a dumb parent_recipe_id on today’s clone is a cheaper first cut if full deltas feel early.
Confidence 80% Complexity Medium
Idea 3

3. Offline cook packet

Keep app-shell navigations NetworkOnly. When someone opens cooking mode, freeze a dispatch packet — scaled ingredients, resolved steps, allergens, cook-for — into device cache, and persist progress in durable storage instead of tab-scoped sessionStorage. The cook finishes if the basement Wi‑Fi dies.

Description
Intent-scoped cache for recipes opened in Cook (and maybe already on the shopping list). Move cook progress off sessionStorage so a killed tab does not wipe the sauce.
Axis
Cooking and kitchen session
Basis
direct: navigate handler is NetworkOnly; README states recipes still need a network connection while the shopping list stays on device; cook state is sessionStorage.setItem(storageKey(recipeId), …).
Rationale
A cook-along that blanks mid-recipe is worse than no cook-along. Offline-the-whole-PWA is a platform project; offline-the-landing is a kitchen-safety rule.
Downsides
Cache invalidation when the author edits; stale allergen data is a safety issue; do not quietly cache the public discover grid.
Confidence 85% Complexity Medium
Idea 4

4. Same-account shopping list sync

The merge engine already knows how to combine quantities by name+unit and keep recipe sources. It only lives on one phone. Sync the cart to the signed-in account so the planner’s phone and the shopper’s phone (same login, then later two logins) see one list. Do not wait on household-owned recipes.

Description
Server-backed shopping list using the existing merge identity and ShoppingSource. First ship: same account, multiple devices. Household membership can come later if two logins become the pain.
Axis
Household sharing and sync
Basis
direct: list key our-recipes-shopping-list in localStorage; merge-by-name+unit already tested across recipes; README documents on-device persistence. external: AnyList won households on live shared lists without shared recipe authorship.
Rationale
Families collide on tonight’s groceries more than on co-editing body markdown. This is the 80% “cook together” without a family OS.
Downsides
Conflict rules if two devices edit offline; migrating localStorage without wiping a full cart; two-login share still needs an invite if same-account is not enough.
Confidence 75% Complexity Medium
Idea 5

5. Allergen exclude on discover

Home already streams public recipes with course and effort selects and paints allergen badges on cards. Add an exclude multi-select over the EU-14 set you already store, and optionally remember it on the profile. Matching recipes drop out of the grid. Badges stop being decoration the cook must interpret under time pressure.

Description
Filter allergens by exclusion on / and /me. Same streamed-load + skeleton pattern as today. Diet and method facets can reuse the control later.
Axis
Browse and classification
Basis
direct: RecipeBrowseFilters exposes only course and effort; cards render compact allergen badges; schema comment is “EU 14 allergens contained in this recipe.”
Rationale
Classification labor today helps curiosity, not safety. Exclusion is the filter a constrained household actually needs first — cheaper than tags or collections.
Downsides
Missing or stale allergen data becomes a false-safe grid; exclusion is not a medical claim and the UI must not pretend it is.
Confidence 90% Complexity Low
Idea 6

6. Tonight cart

Invert “open a recipe and tap ingredients.” Pick one or more recipes and a people count; rebuild the list with the merge and source tracking that already ship. Cooking mode already knows cookFor = baseServings * scaleFactor. The empty-state ritual becomes optional.

Description
A Tonight (or “cook these”) flow that commits recipes + servings and projects the shopping list. Uncommit uses removeRecipeFromList. No week grid.
Axis
Planning and leftovers
Basis
direct: shopping merge sums quantities and merges sources by recipe id; empty copy tells people to open a recipe and tap ingredients; servings exist specifically to scale cooking-mode quantities.
Rationale
The hard part — merge — already shipped. Planning can be “what we committed to cook,” which is a recipe-book move, not a calendar product.
Downsides
Easy to overbuild into a meal planner; keep the object “tonight’s cooks,” not “the week.”
Confidence 70% Complexity Low
Idea 7

7. Cooked! as episodes

recipe_ratings is unique on (recipe, user) and rolled into a public star average. That is a review model. Family cooking is “how Tuesday’s lasagna went,” and it happens again next month. Keep stars as a derived garnish if you want them; store episodes with notes, servings cooked, and a timestamp.

Description
Allow many Cooked! rows per user per recipe. /me/cooked becomes a cook log. Leftover-from-last-cook and “due again” can sit on this log later without a pantry or calendar.
Axis
Cooking and kitchen session
Basis
direct: ratings migration states signed-in 1–5 scores with private notes and public aggregates; uniqueness is (recipe_id, user_id), so a second cook overwrites the first.
Rationale
One row per person blocks leftover history and “make again.” The cook log is the planning seed that does not require inventing a leftovers inventory.
Downsides
Public averages get noisier if every remake is a new score; you may want episode notes without re-scoring, or hide stars on home cards.
Confidence 80% Complexity Medium
